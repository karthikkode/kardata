## Goal
Make the sector research mockup real on a backend that treats files as first-class citizens: every sector feature reads from backend-owned data, every agent-found company lands in Postgres through the `db/` layer, agents stream tokens like a modern chat app, every file ever created is stored in GCS with its reason recorded in the DB index, and any file can be handed to an agent or referenced from a new session. Backend first, then the final sector frontend. No mocks survive on the sector path.

## Success Criteria
- Sector and company researches persist in Postgres and survive restarts; nothing on the sector path reads from `frontend/src/mock/`.
- Researches page (sectors/companies tabs, text filter, state filter), sector detail page (summary, companies, activity, restart-when-failed), dashboard sector/company panels, and the App chat-scope chip all render from staging-API data with the same loading, empty, error, and viewer-denied behavior the mockup demonstrates.
- An agent/tool write path exists: recording a found company or a sector state change is a typed `db/` call that any Temporal activity or MCP tool can use; no route or service touches `pg` directly.
- Live agent replies stream token-by-token to the UI over the existing SSE stream and resolve into one persisted message event; a dropped connection replays from the persisted message, never from a token buffer.
- GCS is the storage layer on staging/prod (filesystem stays for dev/tests only), wired with the previous kardata project's service-account pattern; every stored file carries a recorded reason and producer, is servable only through the DB index, and is re-usable across sessions and agents.
- A subagent-created file is retrievable by the main agent in the same run and referenceable from a brand-new session; the harness asserts GCS-as-storage and DB-as-index on both paths.
- All existing gates stay green and the sector surfaces are verified against Compose, not just unit tests.

## Constraints And Non-goals
- Constraints: all DB access through `db/` barrel; event-log-first writes (new tables are projections, like `threads`); viewer reads vs operator mutations; no direct `pg`, SQL, or secrets in frontend; token deltas are ephemeral stream frames, never event-log rows; docs updated in the same change (`docs/architecture.md`, `docs/implementation-status.md`, `documentation/db.md`, `README.md` only where user-visible behavior changes).
- Non-goals: user-initiated sector creation UI; the deep-research agent pipeline itself (only its DB landing seam); vector/semantic search over files; dashboard email stats; company detail page; touching chat history/approval surfaces except stream rendering and the existing `chatScope` wiring.

## Key Decisions
- **Projection tables, not direct writes.** New `sectors` and `companies` tables are projections over new event types (`sector.created`, `sector.state_changed`, `company.found`, `company.stage_changed`), following the `threads` precedent. Rejected: writing domain rows directly from routes (breaks the event-log-is-the-write-path invariant) and deriving reads by scanning `events` at request time (does not scale to the 60-row overflow lists and dashboard counts).
- **`companiesFound` is computed, never stored.** It is `COUNT(companies WHERE sector_id = …)`, so it cannot drift from the company list the detail page shows.
- **Activity is server-computed from sector events.** The `sectorEvents` derivation logic moves into a repo function so the timeline and the state pill can never disagree; the client stops reconstructing history from a state string.
- **Writes are agent-facing first.** User mutations in phase 1 = restart-failed only (`POST /v1/sectors/:id/restart`, operator role, mirrors the approve-command pattern). Discovery writes (`createSector`, `markCompanyFound`, `setCompanyStage`, `setSectorState`) are typed `db/` repo functions called from Temporal activities/tools with MCP binding rows, not HTTP routes — there is no create button in the mockup to serve.
- **Restart semantics.** Restart appends `sector.state_changed → running`; any live worker converges on the event. Rejected: synchronous worker control from the route.
- **Token deltas ride the outbox, not the event log.** The activity consumes the existing `chatStream`, publishes each `text_delta` as an ephemeral outbox frame, and still appends exactly one message event at completion; the projector publishes the final message frame as today. Rejected: one event per token (write amplification and gapless-seq pressure) and client-side token buffering with no server trail (a reconnect would lose text the user already saw).
- **GCS wiring copies the prior project, not its secrets.** Same three variables (`KARDATA_GCP_ADC_PATH` host mount → `/run/kardata/adc.json:ro`, `KARDATA_GCS_BUCKET`, `KARDATA_GCP_PROJECT_ID`); a `resolveArchiveTarget` used by server and worker picks `GcsTarget` when a bucket is configured, `FilesystemTarget` otherwise, so dev and hermetic tests never need credentials.
- **Provenance is required, not decorative.** The stored-event payload gains a required `reason` (enum: `subagent_output`, `user_upload`, `report`, `proposal`, …), `producedBy` (run/thread key), and source scope; `storeArtifact` rejects reason-less writes. Reference, don't copy: a new session attaches an old file via an `artifact.referenced` event, and serve authorizes tenant scope plus owning-or-referenced — bytes stay single-copy in GCS.
- **Store-then-index is one helper.** `storeAndIndex` replaces bare `storeArtifact` on every production path so "every file is indexed" is structural; the harness asserts stored ⇒ indexed instead of trusting callers.

## Recommended Approach
Phase 0 builds the file-and-stream platform all later work rides on (token deltas → GCS wiring → file index/reuse → harness). Phase 1 builds the sector domain on it. Phase 2 migrates the sector surfaces plus token rendering and file referencing onto `staging-api.ts`, then deletes the sector mocks. Seed demo data through the `db` CLI for Compose acceptance, never through checked-in fixtures.

## Risks / Rollback
- **Projector lag shows stale lists.** Mitigate: reads served from projections carry the same freshness contract as thread lists today; acceptance asserts restart visibility within the documented projector catch-up window.
- **Restart racing a live worker.** The event, not the route, is authoritative; a worker mid-run converges on `running` and acceptance covers restart-while-running.
- **Scope leakage across tenants.** Every repo takes `Scope` and tests assert cross-tenant invisibility, mirroring the session contract; the body route and tenant artifact listing get the same treatment.
- **Delta flood.** A fast provider emits many small frames; mitigation is UI coalescing (append per animation frame), not server throttling, so no text is ever dropped server-side; the snapshot-overflow rule still bounds reconnect cost.
- **GCS outage blocks serve.** Serve is read-through with no local cache in phase 0; a GCS error surfaces as a retryable route/tool error, never as silent empty bytes. A read-through cache is a follow-up, not this plan.
- **Rollback.** Migration `down` drops the two tables; projector rebuild restores them; GCS wiring rolls back to the filesystem target by unsetting the bucket; frontend falls back to mocks only until F-S4 deletion lands, after which rollback means restoring the deleted mock files from git.
